<llmWiki>
    <objective>
        TypeScript implementation of Andrej Karpathy's "LLM Wiki" pattern
        (gist 442a6bf555914893e9891c11519de94f). It keeps three layers in a
        wiki root — immutable `raw/` sources, an LLM-maintained interlinked
        `wiki/` of markdown or HTML pages (chosen per wiki; with a generated
        index and an append-only log), and a schema file (`CLAUDE.md` / `AGENTS.md`) — and
        provides local BM25 / vector / hybrid search over the pages,
        LLM-driven ingest (compile a raw source into a summary page plus
        entity/concept pages), LLM-driven query (answer with citations,
        optionally filed back as a synthesis page), structural and semantic
        lint, and an MCP server so Claude Code / Codex can operate on the
        wiki directly, plus conversion of PDF, DOCX, PPTX and image originals
        into markdown by a dedicated parser LLM (XLSX is converted locally,
        without an LLM; the original is kept unmodified in
        `raw/` and referenced from the markdown's frontmatter `original:`
        field and from the wiki's source page). Intended for indexing and
        searching personal documentation.
    </objective>
    <command>
        llm-wiki <command> [options]
    </command>
    <info>
        ## Overview

        `llm-wiki` turns a folder of raw documents into a self-maintaining,
        cross-linked markdown knowledge base that both humans and LLM agents
        can read, search, and extend. Development usage runs through pnpm;
        after building or linking, the `llm-wiki` binary is available
        directly.

        - `pnpm dev -- <command>` — run from source via `tsx` (no build step)
        - `pnpm build && node dist/cli.js <command>` — run the compiled CLI
        - `llm-wiki <command>` — the OS command, installed with `pnpm link:global` (builds, then links `bin.llm-wiki` → `dist/cli.js` into pnpm's global bin folder, which must be on `PATH`); `pnpm unlink:global` removes it. The link points at this checkout, so `pnpm build` updates the global command.

        ## Built-in guide

        `llm-wiki guide` prints the complete manual, written for people and
        for AI agents (e.g. Claude building a skill). Topics: `overview`,
        `layout`, `selection`, `commands` (generated from the live commander
        definition), `workflows`, `config`, `output` (JSON shapes),
        `errors` (exit codes), `mcp`, `agent-rules`, `skill`.
        `llm-wiki guide <topic>` prints one; `--topics` lists them;
        `--json` returns the topics plus the full command/argument/option
        tree. The prose topics live in `guide/*.md` and ship with the
        package.

        ## Three-layer wiki root layout

        A wiki root is created with `llm-wiki init <dir> --format markdown|html`
        and looks like this (`<ext>` is `.md` or `.html`):

        ```
        raw/            immutable source documents — READ ONLY, never edited or deleted
        raw/assets/     images and attachments belonging to sources
        wiki/           the compiled knowledge base — the LLM owns every file here
          index<ext>    catalog of all pages, generated by `llm-wiki index` (do not hand-edit)
          log<ext>      append-only chronological record (`[YYYY-MM-DD] kind | title` entries)
          overview<ext> optional top-level synthesis of the whole corpus
          wiki.css      HTML wikis only: stylesheet linked by every page (created when missing)
          sources/      one summary page per ingested raw source
          entities/     people, organisations, products, places, projects, tools
          concepts/     ideas, methods, themes, recurring questions
          syntheses/    filed answers, comparisons, analyses, evolving theses
          lint/         dated health-check reports
        .llm-wiki/      tool state (wiki.json = page format, search index, embeddings, ingest ledger) — do not edit
        CLAUDE.md       schema/contract for how the wiki is structured (AGENTS.md is a copy for other agents)
        ```

        ## Page formats

        Each wiki has one page format, fixed at `init` (`--format` or
        `LLM_WIKI_FORMAT`) and recorded in `.llm-wiki/wiki.json`
        (`{"version":1,"format":"markdown"|"html"}`). Wikis without that file
        (created before 0.3) are recognised by their `wiki/index.md` and are
        markdown. The code lives in `src/wiki/format.ts` (`PageFormat`:
        `parse`, `text`, `links`, `prepare`, `render`).

        - **markdown** — `wiki/<id>.md`, YAML frontmatter, `[[wikilinks]]`.
        - **html** — `wiki/<id>.html`, a standalone page for the browser:
          metadata as JSON in `<script type="application/json"
          id="llm-wiki-meta">`, content inside `<main>`, relative
          `<a href>` links, a shared `wiki/wiki.css`, Index/Log navigation and
          a Content-Security-Policy that disables scripts. The index and log
          are `index.html` / `log.html` (log entries are
          `<section class="log-entry">` blocks).

        In both formats pages are authored as YAML frontmatter + body (by
        ingest, `query --file`, MCP `wiki_write_page`). For HTML the body may
        be an HTML fragment or markdown (rendered with `marked`); the tool
        turns `[[wikilinks]]` into relative links, strips scripts, iframes
        and event handlers, and builds the shell. The LLM is shown pages in
        the same frontmatter + body form and the index in markdown.
        `llm-wiki index` / `lint --fix` / MCP `wiki_reindex` convert
        `[[wikilinks]]` left in hand-edited HTML pages. Search indexes the
        text of HTML pages, not their markup.

        ### Markdown page

        ```markdown
        ---
        title: Exact Page Title
        type: entity            # overview | entity | concept | source | synthesis | lint
        summary: One sentence used verbatim in index.md.
        tags: [tag-one, tag-two]
        created: 2026-01-31
        updated: 2026-02-14
        sources: [raw/article.md, raw/paper.md]   # raw files this page draws on
        aliases: [Alt Name]
        ---

        # Exact Page Title

        Body content, using wikilinks such as [[ada-lovelace]] or
        [[entities/ada-lovelace|Ada]] to cross-reference other pages.
        ```

        File names are lowercase kebab-case slugs of the title (e.g.
        `entities/ada-lovelace.md` or `.html`). Every non-obvious claim should cite the
        raw source it came from.

        ## Commands

        | Command | Purpose |
        |---|---|
        | `init <dir> --format markdown\|html [--name n] [--description text] [--use] [--no-register] [--force]` | Scaffold a new wiki root in the chosen page format (required for a new wiki; a markdown wiki can later be converted with `convert --to html`): `raw/`, `wiki/`, `.llm-wiki/wiki.json`, `CLAUDE.md`/`AGENTS.md` written for that format, and register it under `--name` (default: the directory name, slugified). The first registered wiki becomes current; `--use` makes this one current |
        | `wikis [list] [--json]` | List registered wikis with description, page count, pending sources and last log entry; `*` marks the current one |
        | `wikis add <name> <dir> [--description text] [--use]` | Register an existing, initialised wiki root |
        | `wikis use [name]` | Select the wiki commands use when neither `--wiki` nor `--root` is given (no name on a terminal: choose from a list) |
        | `wikis unset` | Clear the selection, so every command must name its wiki |
        | `wikis current` | Print the wiki commands will use and why (flag, env, or selection) |
        | `wikis show [name] [--json]` | Details of one wiki |
        | `wikis rename <old> <new>` / `wikis describe <name> [text]` | Rename / (re)describe a registered wiki |
        | `wikis remove <name>` | Unregister a wiki; its files are never touched |
        | `ingest [files...] [--json] [--force] [--dry-run] [--max-tokens n] [--related n] [--context-chars n] [--max-source-chars n] [--reparse] [--parse-max-tokens n] [--max-bytes n] [--max-images n]` | LLM-driven compile of one or more raw sources into `sources/`, `entities/`, `concepts/` pages. PDF/DOCX sources are converted first with the parser LLM to `raw/<name>.pdf.md` / `raw/<name>.docx.md`, then ingested; `--reparse`, `--parse-max-tokens` and `--max-bytes` tune that conversion step |
        | `parse <files...> [--json] [--force] [--max-tokens n] [--max-bytes n] [--max-images n]` | Convert PDF, DOCX, PPTX, XLSX and image (PNG, JPEG, GIF, WebP) originals into markdown without ingesting them: PDF/DOCX/PPTX/images with the dedicated parser LLM (PPTX: slides read locally plus up to `--max-images` slide pictures; images need a vision model), XLSX locally with no LLM (one markdown table per sheet, exact values). Without ingesting them into the wiki |
        | `query "<question>" [--json] [--file] [--limit n] [--pages n] [--mode bm25\|vector\|hybrid] [--max-tokens n] [--wikis a,b \| --all-wikis]` | LLM-driven answer with citations; `--file` also saves it as a `syntheses/` page. With `--wikis`/`--all-wikis` the answer draws on several wikis (rank-fused search, shared page budget, citations `[[wiki:page-id]]`, a log entry in each wiki; `--file` refused) |
        | `search "<query>" [--mode bm25\|vector\|hybrid] [--limit n] [--layer wiki\|raw\|all] [--wikis a,b \| --all-wikis] [--json]` | Local full-text / semantic search over pages (and optionally raw sources) of the selected wiki, or of several registered wikis at once (rankings merged with reciprocal-rank fusion, each hit labelled with its wiki) |
        | `index [--raw] [--embed] [--json]` | Regenerate the index (`index.md` / `index.html`) and the search index; in HTML wikis first convert leftover `[[wikilinks]]`; `--embed` also (re)computes embeddings |
        | `lint [--llm] [--fix] [--report] [--json]` | Structural (and, with `--llm`, semantic) health check; writes `lint/<date>.md` |
        | `convert --to html [--dry-run] [--keep-schema] [--json]` | Convert the selected markdown wiki to HTML in place: pages keep ids and metadata, `[[wikilinks]]` / `[text](x.md)` links become relative `.html` links, log/index/search index are rebuilt; The markdown files (pages, `index.md`, `log.md`, replaced schema files) are moved to `.llm-wiki/backup/markdown-<timestamp>/`. A customised `CLAUDE.md`/`AGENTS.md` is merged (template sections replaced, custom sections kept) unless `--keep-schema`. No LLM call |
        | `sources check [--json]` / `sources update [--dry-run] [--json]` | Compare every outside source (downloaded URLs, files ingested from outside the wiki) with its latest raw copy by SHA-256 — URLs via a conditional request first, web pages by the hash of their readable or rendered text — and re-ingest the changed ones as new dated raw originals |
        | `pages [--type t] [--json]` | List the pages of the selected wiki: id, path, title, type, summary, updated, sources |
        | `show <page> [--json]` | One page for viewers: metadata, the body as sanitised HTML with `llmwiki://open?wiki=&page=` / `&raw=` links, outgoing links, backlinks, source files |
        | `graph [--json]` | The whole wiki as a graph for viewers: pages (with their link counts), page-to-page links, the source files each page cites, broken links; without `--json`, counts, hubs and unlinked pages |
        | `log [--last n] [--kind k] [--json]` | Show recent entries from `wiki/log.md` / `wiki/log.html` |
        | `guide [topic] [--topics] [--json]` | Print the complete manual for people and AI agents (see "Built-in guide") |
        | `config` | Print resolved configuration and which tier (shell / tool-agents / local / CLI) each value came from |
        | `mcp` | Run as an MCP server exposing `wiki_search`, `wiki_read_page`, `wiki_write_page`, `wiki_log`, etc. |

        Global options (available on every subcommand except `init`):

        - `--wiki <name>` — registered wiki to work on; overrides `LLM_WIKI_NAME` and the current selection
        - `--root <dir>` — wiki root directory; overrides `LLM_WIKI_ROOT` (an alternative to `--wiki`; passing both is an error)
        - `--pick` — choose the wiki interactively from the registry for this one command
        - `--provider <name>` — chat provider; overrides `LLM_WIKI_PROVIDER`
        - `--model <name>` — chat model; overrides `LLM_WIKI_MODEL`

        ## Configuration

        Every command except `init` and `wikis` operates on one wiki,
        chosen in this order (nothing is ever guessed):

        1. `--wiki <name>` / `LLM_WIKI_NAME` or `--root <dir>` /
           `LLM_WIKI_ROOT`. If both a name and a root are set, the one from
           the higher configuration tier wins; both in the same tier is an
           error.
        2. The registry's current selection (`llm-wiki wikis use <name>`).
        3. On an interactive terminal with registered wikis, a prompt asks
           which wiki to use. Otherwise the command fails with a
           configuration error listing the registered wikis.

        Every command prints the chosen wiki on stderr (`wiki: <name> —
        <root>`). Commands that call an LLM
        (`ingest`, `query`, `lint --llm`) additionally require
        `LLM_WIKI_PROVIDER` and `LLM_WIKI_MODEL`; `index --embed` and
        `search --mode vector|hybrid` additionally require
        `LLM_WIKI_EMBEDDING_PROVIDER` and `LLM_WIKI_EMBEDDING_MODEL`;
        `parse`, and `ingest` of a `.pdf`/`.docx` source, additionally
        require `LLM_WIKI_PARSER_PROVIDER` and `LLM_WIKI_PARSER_MODEL`.

        | Variable | Purpose |
        |---|---|
        | `LLM_WIKI_NAME` | Name of a registered wiki to operate on. Optional; overridable with `--wiki`. |
        | `LLM_WIKI_ROOT` | Absolute path of a wiki root (registered or not). Optional when a wiki is selected by name or by `wikis use`; overridable with `--root`. |
        | `LLM_WIKI_BROWSER` | Absolute path of a Chromium-family browser (Chrome, Chromium, Edge, Brave). Needed only to ingest/parse web pages that build their content with JavaScript (or with `--render`), which are printed to PDF headless; the tool raises a configuration error naming this setting (and the browsers it found) when such a page is met without it. |
        | `LLM_WIKI_FORMAT` | Page format of a wiki being created: `markdown` or `html`. Required by `init` for a new wiki (no default); overridable with `init --format`. Ignored for existing wikis, whose format is recorded in `.llm-wiki/wiki.json`. |
        | `LLM_WIKI_PROVIDER` | Chat provider used by `ingest` / `query` / `lint --llm`. One of `openai`, `anthropic`, `gemini`, `azure-openai`, `azure-anthropic`, `ollama`, `litellm`, `mlx`. Overridable with `--provider`. |
        | `LLM_WIKI_MODEL` | Chat model name (e.g. `claude-opus-5`, `gpt-5`, `gemini-2.5-pro`, `llama3`). For `azure-openai` the deployment comes from `AZURE_OPENAI_DEPLOYMENT` instead. Overridable with `--model`. |
        | `LLM_WIKI_EMBEDDING_PROVIDER` | Provider for embeddings used by `index --embed` and vector/hybrid search. One of `openai`, `gemini`, `azure-openai`, `ollama`, `litellm`, `mlx` (Anthropic providers cannot embed). Optional — BM25 search works without it. |
        | `LLM_WIKI_EMBEDDING_MODEL` | Embedding model (or Azure deployment) name, e.g. `text-embedding-3-small`, `gemini-embedding-001`, `nomic-embed-text`. Required only when `LLM_WIKI_EMBEDDING_PROVIDER` is set. |
        | `LLM_WIKI_PARSER_PROVIDER` | Dedicated provider for converting PDF, DOCX, PPTX and image originals into markdown (`parse`, and `ingest` of such a source; not needed for `.xlsx`). Images and PPTX pictures need a model with vision. One of the eight standard providers. Required only when a PDF/DOCX is parsed. |
        | `LLM_WIKI_PARSER_MODEL` | Model name for the parser provider (for `azure-openai`, the deployment name). Required together with `LLM_WIKI_PARSER_PROVIDER`. |

        `llm-wiki` supports all eight standard LLM providers via
        vendor-canonical environment variable names (never prefixed with
        `LLM_WIKI_`):

        - **OpenAI** — `OPENAI_API_KEY`, `OPENAI_BASE_URL`, `OPENAI_ORG_ID`
        - **Anthropic** — `ANTHROPIC_API_KEY`, `ANTHROPIC_BASE_URL`
        - **Gemini** — `GOOGLE_API_KEY` (alias: `GEMINI_API_KEY`)
        - **Azure OpenAI** — `AZURE_OPENAI_API_KEY`, `AZURE_OPENAI_ENDPOINT`, `AZURE_OPENAI_DEPLOYMENT`, `AZURE_OPENAI_API_VERSION`
        - **Azure Anthropic (Foundry)** — `AZURE_AI_INFERENCE_KEY`, `AZURE_AI_INFERENCE_ENDPOINT`
        - **Ollama** — `OLLAMA_HOST`
        - **LiteLLM proxy** — `LITELLM_PROXY_URL`, `LITELLM_MASTER_KEY`
        - **MLX-LM** — reuses `OPENAI_BASE_URL` (no dedicated env var)

        Configuration resolves through a four-tier chain, lowest to highest
        priority:

        1. Shell-registered env vars (`process.env`)
        2. `~/.tool-agents/llm-wiki/.env`
        3. Local `.env` in the current working directory
        4. CLI flags (always win)

        On startup the tool creates `~/.tool-agents/llm-wiki/` (mode `0700`)
        and an empty `.env` (mode `0600`) if they do not already exist
        (`src/config/env.ts`, `ensureToolConfigDir()`). There are no
        fallback defaults for missing configuration — a required setting
        that is absent from every tier raises a `ConfigError` naming the
        setting and where to set it. Run `llm-wiki config` to see the
        resolved value and source tier for every setting.

        ## PDF / DOCX originals

        Raw sources are not limited to markdown/text: dropping a `.pdf` or
        `.docx` file into `raw/` and running `llm-wiki ingest` (or
        `llm-wiki parse` to convert without ingesting) converts it to a
        markdown sibling using a dedicated **parser LLM**, configured
        separately from the chat provider via `LLM_WIKI_PARSER_PROVIDER` /
        `LLM_WIKI_PARSER_MODEL` so a cheaper/faster or document-native
        model can be used just for conversion.

        - **Native document support** — `anthropic`, `azure-anthropic`,
          `gemini`, `openai`, `azure-openai` and `litellm` receive the PDF
          bytes directly. `ollama` and `mlx` cannot read PDFs natively, so
          the tool first extracts text locally with `pdf.js`. DOCX is
          always converted to HTML locally with `mammoth` before being
          sent to any provider (no provider reads `.docx` natively).
        - **Output naming** — the original's extension is kept in the
          markdown filename so PDF and DOCX siblings never collide:
          `raw/report.pdf` → `raw/report.pdf.md`,
          `raw/report.docx` → `raw/report.docx.md`. The original file
          itself is never modified.
        - **Provenance frontmatter** — the generated markdown carries:
          `original` (path of the source document, relative to the wiki
          root), `original_type` (`PDF` or `DOCX`), `original_sha256`
          (content hash of the original bytes), `parsed_by`
          (`<provider>/<model>` that performed the conversion), and
          `parsed_at` (the conversion date). Immediately below the
          frontmatter the file opens with a note in the form
          `> Converted from the original PDF document [[raw/report.pdf]]
          (…KB, sha256 …) by <provider>/<model> on <date>.` so the
          provenance is visible to both humans and agents reading the
          markdown directly.
        - **Wiki-side provenance** — when `ingest` compiles a converted
          document, the resulting `wiki/sources/<slug>.md` page also gets
          an `original:` frontmatter field pointing at the raw original,
          and its body links to `[[raw/report.pdf]]` explicitly, so the
          original is discoverable from both the raw markdown and the
          wiki page.
        - **Caching by hash** — conversions are cached in
          `.llm-wiki/parsed.json`, keyed by the original file's content
          hash. Re-running `ingest`/`parse` on an unchanged original is a
          no-op; pass `--reparse` (on `ingest`) or `parse --force` to
          redo the conversion even when the cached markdown is already up
          to date (e.g. after switching parser provider/model).
        - **Size limits** — originals above `--max-bytes` (default 30 MB)
          are refused rather than truncated; split the document instead.
          If local extraction (for `ollama`/`mlx`) yields no text — e.g. a
          scanned image PDF — the tool raises an error naming a
          native-PDF provider to use instead.

        ## Examples

        ```bash
        # 1. Create wikis; each is registered by name, the first becomes current
        llm-wiki init ~/notes/wiki --format markdown --name notes --description "Personal notes"
        llm-wiki init ~/work/wiki --format html --name work --description "Work documentation"
        llm-wiki wikis                       # list them
        llm-wiki wikis use work              # make "work" the default
        llm-wiki --wiki notes search "sourdough"   # or name the wiki per command
        llm-wiki search "kubernetes" --all-wikis   # search every wiki at once
        export LLM_WIKI_ROOT=~/notes/wiki    # an explicit root still works

        # 2. Drop a source document into raw/, then ingest it
        cp ~/Downloads/paper.pdf.md $LLM_WIKI_ROOT/raw/
        llm-wiki ingest raw/paper.pdf.md --provider anthropic --model claude-opus-5

        # 2b. A PDF/DOCX/PPTX/image original is converted by the parser LLM first
        #     (an XLSX locally, without an LLM),
        #     then compiled into the wiki like any other source
        cp ~/Downloads/report.pdf $LLM_WIKI_ROOT/raw/
        export LLM_WIKI_PARSER_PROVIDER=gemini LLM_WIKI_PARSER_MODEL=gemini-2.5-pro
        llm-wiki ingest raw/report.pdf --provider anthropic --model claude-opus-5

        # 2c. Or just convert without ingesting (writes raw/report.pdf.md);
        #     --force redoes it even if the cached markdown is current
        llm-wiki parse raw/report.pdf --force

        # 3. Regenerate the index and (optionally) embeddings
        llm-wiki index --embed --provider openai

        # 4. Search locally (no LLM call)
        llm-wiki search "transformer attention" --mode hybrid --limit 10

        # 5. Ask a question, filing the answer as a synthesis page
        llm-wiki query "How does attention differ from RNN gating?" --file

        # 6. Run structural + semantic lint and write a report
        llm-wiki lint --llm --report

        # 7. Inspect recent activity
        llm-wiki log --last 10

        # 8. Check resolved configuration and its source tier
        llm-wiki config
        ```

        ## MCP registration (Claude Code)

        ```bash
        claude mcp add llm-wiki -- llm-wiki mcp
        ```

        This exposes wiki operations (`wiki_list_wikis`, `wiki_search`,
        `wiki_read_page`, `wiki_list_pages`, `wiki_write_page`,
        `wiki_append_log`, `wiki_recent_log`, `wiki_lint`,
        `wiki_reindex`) directly to Claude Code / Codex. Every tool takes
        an optional `wiki` name; `wiki_search` also accepts `wikis` (a list,
        or `["*"]` for all). Calls without a name use the server's default
        wiki, resolved at start-up like any command (`--wiki`, `--root`,
        env, or the current selection); with no default, every call must
        name its wiki. The agent calls `wiki_list_wikis` to decide which
        wiki to update or query. The registry is re-read on every call.

        ## Wiki registry

        Registered wikis live in `~/.tool-agents/llm-wiki/wikis.json`
        (mode 0600): name, absolute root, optional description, date
        registered, and the current selection. The registry stores no
        content; removing an entry never deletes files. A corrupt registry
        is reported as an error, never reset silently.
